2.3 Mock do bridge PyWebView
----------------------------

Arquivo: UI/e2e/fixtures/pywebview-bridge-mock.ts (100 linhas).
- Linha 6: createPyWebViewMockScript(options) devolve uma string JS que
  define window.pywebview.api (injetada com page.addInitScript).
- Linhas 1-4: opções askLatencyMs e simulateLlmTimeout.
- Linha 32: sendMessage devolve sempre a mesma frase, com
  "Recuperação híbrida via BM25 e ChromaDB." e
  "Citações obrigatórias e verificadas.".
- Linhas 34-39: listNotes devolve 2 notas fixas.
- Linhas 57-65: getDoctor devolve status ok para sqlite e chroma.
- Linhas 86-95: runBenchmarkCompare devolve MRR fixo.

O que isso significa: o E2E testa a UI React contra um bridge falso. O
backend Python não roda. Logo, os specs provam renderização e fluxo de
tela, não a qualidade do RAG nem a lógica do pipeline. Os testes de
backend real ficam no pytest.

Complexidade: o mock precisa cobrir todos os métodos que a UI chama. Um
método faltando gera erro no console; AUDIO_VALIDATION.md:64-66 registra
um scanVault faltando. Além disso, o React lê window.pywebview ao carregar
o módulo (docs/spec-kit/playwright-e2e-suite-plan.md, linhas 6-7). Por
isso o mock precisa ser injetado antes do bundle, via addInitScript.
