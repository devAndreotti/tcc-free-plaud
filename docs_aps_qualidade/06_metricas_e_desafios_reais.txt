2. DESAFIOS E DIFICULDADES REAIS
--------------------------------

Cada item traz o problema, a evidência e o que foi feito.

2.1 Testes instáveis na TUI (Textual)
- Problema: teste depende de tempo (pilot.pause e thread). Falha
  aleatória sem mudança de código.
- Evidência:
  - PR #118, run 38563746866: falhou em
    test_tui_ask_button_ignores_double_click_while_running com
    "assert ['hybrid','hybrid'] == ['hybrid']" (pipeline/tests/test_tui_app.py:714-743).
    Passou na reexecução (14m47s) (fatos).
  - Pytest completo na VPS: falhou
    test_tui_notes_cancel_button_cancels_running_index
    (test_tui_app.py:1154). Passou 3/3 isolado (fatos).
  - As esperas são fixas: pilot.pause(0.5) em test_tui_app.py:738, além de
    outras esperas de 0,1 a 0,5 s no mesmo arquivo.
- O que foi feito: reexecução manual. Não há retry automático no pytest.
  git log --grep=flaky (e instav) não retorna nenhum commit.

2.2 Runner de 1 slot (fila de jobs)
- Problema: um único runner executa todos os jobs de todos os PRs em série.
- Evidência: fatos (runner hermes-ostg02-tcc-runner, 1 slot). Security
  audit chegou a 16m38s esperando cache (run 38563746866).
- Efeito no código: concurrency cancel-in-progress (quality-gate.yml:9-11)
  cancela runs antigas. Resultado: 14 cancelled entre 99 runs (1.2).
- O que foi feito: cache do uv desligado (enable-cache: false) e cache
  movido para o volume do workspace (quality-gate.yml:33-35). O comentário
  do workflow diz que o /home do runner encheu e deixou entradas
  incompletas no cache, e que no mesmo disco o uv usa hardlink.

2.3 Incidente de disco cheio no runner (2026-10-13)
- Problema: o volume do runner lotou. Jobs falharam com "No space left on
  device" ou travaram cerca de 10 min sem executar passos (fatos).
- Causas: venv de 6,6 GB; runner antigo 2.322.0 (1,25 GB) sem remoção;
  logs _diag antigos; runner duplicado (fatos).
- Causa de fundo: o uv.lock fixava torch CUDA (+ ~3 GB de bibliotecas
  NVIDIA) também no runner ARM, sem GPU. Ver commit b6a8b49 (item 2.8).
- O que foi feito: limpeza, volume de 100% para 65% (fatos). Disco raiz
  da VM em 94% e volume de 50 GB em 83% em 2026-10-14 (fatos).
- Impacto medido: Build & smoke 56,9 min e Docker gate 52,7 min nas runs
  de 2026-10-13 (1.4).

2.4 Secrets do Dependabot e SonarCloud
- Problema: PRs do Dependabot não recebem secrets. Sem SONAR_TOKEN, o
  job SonarCloud falha sempre.
- Evidência: 4 das 8 falhas verificadas (1.5) são PRs do Dependabot.
- O que foi feito: consolidar as atualizações em um PR único:
  - commit b0e02a9, "chore(deps): consolida as atualizações do Dependabot
    (#113)";
  - commit 7da8203, "chore(deps): consolida as atualizações do Dependabot
    (#114-#117) (#118)".

2.5 Falhas do servidor SonarCloud
- Problema: análises da main falham desde 2026-10-08 com "CE Task finished
  abnormally" (fatos; run 37867326230).
- Efeito: a última métrica válida da main é de 2026-07-21 (sonar_raw.txt).
  Sem análise nova, as métricas da main ficam defasadas.
- Diferença: o relatório de 2026-07-21 mostra ncloc 16.686, cobertura

- O que foi feito: nada no repo. Pendente: abrir caso no SonarCloud ou
  reexecutar a análise.

2.6 Renomeação que virou "código novo" no Sonar (PR #119)
- Problema: o rename do projeto (free-plaud para Escólio) fez todo o
  código aparecer como novo para o SonarCloud.
- Evidência: run 38576721730 falhou com Security Rating C on New Code.
  Causa: a issue antiga python:S2245 (PRNG em
  pipeline/src/escolio/benchmark/metrics.py, linha ~157, bootstrap de
  intervalo de confiança com seed fixa) entrou no cálculo (fatos).
- O que foi feito: o dono marcou a issue como falso positivo, com
  justificativa. A reexecução passou. Sem mudança de código.
- Risco: um falso positivo marcado à mão. Se o código mudar, a marcação
  precisa ser revista.

2.7 Lockfile com CRLF
- Problema: UI/package-lock.json é versionado com CRLF. npm e o
  Dependabot regravam em LF, e o diff vira o arquivo inteiro (fatos).
- O que foi feito: restaurar o CRLF antes de commitar. Procedimento
  manual; não há checagem automática no workflow.

2.8 torch CPU em ARM (PR #103)
- Problema: sentence-transformers puxa torch. O marcador
  "extra == 'gpu-cu128'" nas sources não separava a resolução, e o
  uv.lock fixava torch CUDA em Linux e Windows (commit b6a8b49).
- Efeito: no runner ARM, sem GPU, ~3 GB de bibliotecas NVIDIA a cada
  execução, enchendo o disco.
- O que foi feito: extras "cpu" (índice pytorch-cpu) e "gpu-cu128"
  declarados como conflitantes, com "extra =" nas sources. Quality gate e
  desktop-release usam --extra cpu (pipeline/pyproject.toml; commit b6a8b49).

2.9 Regressão do undici no Node 20.20 (commit 97b1ece)
- Problema: undici markAsUncloneable falhava no Node 20.20 (mensagem do
  commit 97b1ece).
- O que foi feito: node-version subiu para 22, no PR #93 (fatos).

2.10 Mock do bridge PyWebView no E2E
- Problema: o app é um pywebview. Sem o bridge, a UI cai no fallback.
  O React lê window.pywebview ao carregar o módulo
  (docs/spec-kit/playwright-e2e-suite-plan.md, linhas 6-7). O mock tem
  que chegar antes do bundle (addInitScript).
- Evidência: o mock tem que cobrir todos os métodos chamados
  (UI/e2e/fixtures/pywebview-bridge-mock.ts). Faltou scanVault em uma
  rodada (AUDIO_VALIDATION.md:64-66). Três specs (04, 05, 06) fazem só
  smoke (parte 04, 2.1).
- O que foi feito: branch fix/e2e-backend-real e PR #102 ("correções do
  teste ponta a ponta com o backend real"). Esse PR usou o backend real
  com dados isolados e achou bugs de dados (reindex trocava note_id;
  benchmark gravava no corpus do usuário).

2.11 Modelo de embedding divergente no corpus real
- Problema: o índice real foi gerado com chroma-default, mas a

  (service.py:998). Experimento 14 valida o caminho com corpus temporário
  (docs/experimentos/14_consistencia_reset_rebuild_corpus.md, linhas 65-66).
